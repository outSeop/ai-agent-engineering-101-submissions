# 언어모델·하네스 검토 — 2026-11-02

현재 구현은 모델이 가격과 행동을 고르고 코드가 실행하는 구조다. 영수증과 정산의 구분,
일회성 모델 호출, 구조화 출력은 갖췄다. 다만 운영 전에 상태 수명, 출력의 의미 검증,
시간 예산을 보완해야 한다. 아래는 검토 결과이며 제품 코드 수정은 포함하지 않는다.

## 실행 전 수정할 항목

1. **P1 — 중단된 협상이 재고를 계속 예약한다.** `Seller.available()`은 모든
   `self.open`의 단위를 제외하지만 `opened_at`을 이용한 만료 처리가 없다.
   24시간 지난 협상을 넣어도 판매 가능 재고가 0개로 남는 것을 재현했다.
   협상별 마지막 활동 시각, 만료, 취소, 서명 후 보류를 구분하고 만료 시 재고를 반환해야 한다.

2. **P1 — 잘못된 단위 선택을 다른 단위로 대체하면서 가격은 유지한다.**
   seller의 `unit_id` 스키마는 임의 문자열을 허용한다. 존재하지 않는 ID와 가격 1을
   반환하게 하자 첫 재고를 가격 1에 제시했다. JSON 형식 준수와 실행 의미의 유효성은
   별개다. 허용 단위 enum과 행동별 필드 검사를 하고, 실패하면 해당 응답을 실행하지
   않아야 한다. 마감 여유가 있으면 오류 이유를 제공하는 수정 요청을 한 번 할 수 있다.

3. **P1 — 모델 호출이 남은 주문 시간을 받지 않는다.** `decide_json()`은 전역
   60초 제한만 쓴다. buyer는 70.1초가 남으면 모델을 호출할 수 있어 모델이 60초를
   쓰면 seller 응답에 10.1초밖에 남지 않는다. 이미 만료된 주문에서도 가게 선택
   모델을 호출하는 것을 재현했다. 선택 전 마감 확인, 호출별 남은 시간 전달,
   다음 네트워크 단계와 정산을 위한 시간 확보가 필요하다. seller의 모델 호출도
   동시 실행 한도와 취소 처리가 없다. 부하 상황의 실제 실패율은 아직 측정하지 않았다.

4. **P2 — 컨텍스트의 거래 수만 제한하고 거래 안의 길이는 제한하지 않는다.**
   후속 조치(2026-11-03): 거래 내 제안·맞제안은 최근 4개와 전체 개수로 압축하고,
   과거 메모리에 UTF-8 바이트 예산을 적용했다. 동일 SKU·등급의 기억도 공유한다.
   아래 설명은 검토 당시의 상태이며, 이 항목은 현재 구현에서 보완됐다.
   `compact_context()`는 최근 12건을 고르지만 각 거래의 제안·맞제안은 전부 유지한다.
   거래 1건에 제안 2,000개를 넣자 2,000개가 모두 전달됐고 직렬화 크기는 11,428바이트였다.
   마지막 몇 회와 제안 횟수·최소·최대·최종값을 전달하고 전체 입력 크기도 제한해야 한다.
   각 후보마다 전체 이벤트 로그를 다시 읽는 비용도 기록 증가에 따라 커진다.

## 모델 판단과 학습을 보강할 항목

5. **P2 — 첫 선택의 판단이 다음 협상으로 이어지지 않는다.** buyer의 가게 선택
   이유는 로그에만 남고 다음 프롬프트에는 최근 seller 메시지와 마지막 제안만 들어간다.
   목표 가격, 중단 조건, 이전 제안 요약, 선택 근거를 작은 협상 상태로 유지하는 편이 좋다.
   첫 제안 70~85% 범위는 실험 정책이며 예산 상한과 같은 필수 결제 조건으로 취급하면 안 된다.

6. **P2 — 수요 예측에 필요한 시간과 노출 정보가 부족하다.** restock은 누적
   요청·정산 수를 보여 주지만 관측 기간, 재고가 있었던 시간, 해당 기간의 가격을
   보여 주지 않는다. 따라서 모델이 출력한 수요 평균은 측정된 수요가 아니라 가설이다.
   최근 시간 창의 관측과 노출을 제공하고, 근거 없는 수요 추정과 소량 탐색 구매를
   별도 행동으로 표현해야 한다. 모든 근거가 없을 때 계속 보류하면 초기 학습이 막힐 수 있다.

7. **P2 — 모델의 실제 기여와 비용을 측정하기 어렵다.** 입력·응답·소요 시간은
   있지만 프롬프트 버전, 결정 ID, 토큰 사용량, 모델이 도구를 호출했는지, 수정·대체율을
   일관되게 기록하지 않는다. CLI의 `--json` 이벤트를 이용한 계측을 검토할 수 있다.
   `read-only`는 모델 생성 명령의 쓰기를 제한하는 설정이며 도구 제거 설정이 아니다.
   현재 도구 호출 억제는 프롬프트에 의존하고 있어 실제 호출 여부를 관측해야 한다.
