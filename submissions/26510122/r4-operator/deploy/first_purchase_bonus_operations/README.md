# First-purchase extra loyalty credit

The genuine `first_purchase_bonus` v4 tool was authored and self-tested by official Mind through the development CLI. Exact source is frozen in `../first_purchase_bonus_runtime_v4/`; its build manifest is historical, while live activation is a separate private policy/worker opt-in. Operating decisions remain on the classroom market model. External code is only the settlement event feed, capability boundary and worker wiring. Failed earlier genuine versions are evidence, not production fallbacks.

After verified settlement and delivery the first verified payment wallet receives `base*5//100` extra shop credit, capped at 5,000. The original 1% accrual is unchanged and rounded separately. Lifetime grants total at most 50,000, policy windows at most 72 hours. The earliest verified settlement determines first-purchase eligibility; a new bearer code, new policy name, repeat execution, or refund does not reset it. Existing lot expiry is preserved; absent small-value lots use the verified settlement timestamp plus seven days. Credits are for later purchases, with the existing redemption floor and refund/debt accounting. No wallet transfer is authorized by the bonus tool.

Live files are private under round-4: `state/r4-benefits/first-purchase-bonus-policy.json` has exactly enabled/id/start/end/lifetime_budget; `.kit/first-purchase-bonus-activation.json` has initial_event_cursor/tool_version. Do not copy an old active policy into a fresh environment or reset the award table. Use a reviewed event cursor that cannot skip in-window events. The original worker opt-in is `--first-purchase-bonus <absolute root>/.kit/first-purchase-bonus-activation.json`. Its callback processes only committed settled_and_earned identifiers with keyless original SDK invocation. Inactive, unverified or temporary results defer the bonus feed while original reconciliation continues.

Rollback disables the policy or removes only the known worker opt-in and restores code from the private activation backup. Preserve all sale IDs, JWTs, lots, allocations, welcome_award rows and checkpoints; never restore the DB as a code rollback. The independent refund fixture checks confirmed-refund bookkeeping only, not a new live refund approval/transfer integration.
